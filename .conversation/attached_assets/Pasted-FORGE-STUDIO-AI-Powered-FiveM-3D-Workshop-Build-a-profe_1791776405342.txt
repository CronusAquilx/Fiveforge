FORGE STUDIO — AI-Powered FiveM 3D Workshop

Build a professional, functional, responsive web application called FORGE STUDIO. This is a browser-based 3D asset workshop designed primarily for FiveM vehicle creators, GTA V modders, and 3D artists.

The initial release must focus on four core features:

1. A fully functional interactive 3D viewport.
2. Real 3D model importing.
3. Real model exporting.
4. Texture importing, viewing, editing, and exporting.

This must be a working application, not a static UI mockup. Prioritize functional file handling and correct 3D rendering alongside a premium interface.

1. VISUAL DESIGN

Create a high-end professional interface inspired by modern 3D modeling software, automotive design studios, and premium developer tools.

Design requirements:

* Dark charcoal and matte black interface.
* Refined gray borders and separators.
* White typography with restrained accent colors.
* Compact professional controls.
* Consistent spacing and alignment.
* Smooth, subtle transitions.
* Minimal visual clutter.
* Professional icons.
* Clear tooltips for icon-only buttons.
* No excessive rounded cards, oversized headings, cartoonish graphics, or generic SaaS layouts.

The application should feel like a serious piece of desktop software adapted for the browser.

Create a custom FORGE STUDIO wordmark using typography and a simple geometric icon. Do not use copied brand logos.

Desktop layout

At desktop resolutions, use a professional editor layout:

* Top toolbar: logo, project name, file operations, undo, redo, viewport controls, and export.
* Left sidebar: asset browser, imported files, object hierarchy, and scene objects.
* Center: large interactive 3D viewport.
* Right sidebar: object properties, material information, and texture controls.
* Bottom panel: processing status, warnings, file information, and operation logs.

Allow sidebars to collapse so the viewport can occupy more space.

Mobile layout

The application must be genuinely usable on phones, not simply shrink the desktop interface.

* Use a compact top navigation bar.
* Give the 3D viewport most of the available screen.
* Use bottom navigation or slide-out panels for Assets, Objects, Materials, and Settings.
* Put secondary tools inside compact menus or bottom sheets.
* Make buttons touch-friendly.
* Support touch rotation, pinch-to-zoom, and two-finger panning where practical.
* Support portrait and landscape orientations.
* Prevent panels from overflowing the screen.
* Make upload, texture replacement, project saving, and export usable on mobile.
* Do not require hovering to access essential features.

Use responsive layouts and test at approximately 390px, 768px, 1280px, and 1920px wide.

2. REAL 3D VIEWPORT

Use React, TypeScript, and Three.js, with React Three Fiber if appropriate.

Implement a real WebGL-based 3D viewport.

Required features:

* Orbit around the model.
* Zoom in and out.
* Pan the camera.
* Reset the camera.
* Frame the selected object.
* Fit the entire model to the viewport.
* Toggle grid and axes.
* Toggle wireframe display.
* Switch between perspective and orthographic cameras.
* Change viewport backgrounds.
* Display a ground grid and lighting environment.
* Support object selection.
* Highlight selected objects.
* Display model loading progress.
* Display helpful error messages when files fail to load.
* Dispose of unused geometry, textures, and materials when replacing models.

Use OrbitControls or an equivalent implementation.

Provide a clean empty state with an import action when no model is loaded.

Do not use static screenshots or rendered car images as substitutes for actual 3D models.

3. MODEL IMPORTING

Implement a working file import pipeline.

Start with these formats:

* GLB
* GLTF
* OBJ
* STL
* FBX, if compatible libraries and dependencies are available.

Use appropriate loaders for each format. Support associated OBJ material files and textures when available. If an asset requires companion files, clearly explain which files are missing.

Support importing from:

* The device file picker.
* Drag and drop on desktop.
* The file picker on mobile.

After import:

1. Validate the file type and size.
2. Load the actual model into the 3D scene.
3. Preserve the geometry and supported material information.
4. Center and frame the model.
5. Update the scene hierarchy.
6. Display the filename, dimensions, object count, triangle count when available, and material count.
7. Display errors when the file is invalid or unsupported.

Allow multiple supported objects to be imported into the same scene without replacing existing objects unless the user chooses to replace the scene.

Use appropriate file size limits and handle memory errors gracefully.

4. SCENE HIERARCHY AND OBJECT TOOLS

Create a real scene hierarchy panel.

Features:

* List objects in the current scene.
* Select an object from the hierarchy or viewport.
* Rename objects.
* Hide and show objects.
* Lock objects against accidental selection.
* Delete objects with confirmation.
* Duplicate objects.
* Group and ungroup objects where appropriate.
* Select multiple objects where supported.
* Display object names and visibility states.

Add a transform inspector for the selected object:

* Position X, Y, Z.
* Rotation X, Y, Z.
* Scale X, Y, Z.
* Apply changes immediately to the actual scene.
* Include reset controls.
* Include a way to undo and redo supported changes.

Ensure the inspector and viewport always reflect the same underlying scene state.

5. TEXTURE STUDIO

Build a functional texture and material editing panel.

Support common image formats:

* PNG
* JPEG
* WebP
* Other browser-supported image formats where practical.

Implement:

* Import texture files.
* Display texture previews.
* List textures associated with imported materials.
* Select a material and inspect its properties.
* Replace a material’s base-color texture.
* Change base color.
* Adjust roughness and metalness where supported.
* Toggle texture visibility for inspection.
* Adjust texture repeat and offset where supported.
* Preview changes immediately on the actual 3D model.
* Revert material changes.
* Export the edited texture as an image file.
* Export supported model formats with their associated edited materials and textures.

Handle color-space settings correctly for color textures. Do not treat normal maps and other data textures as ordinary color images.

When a texture is missing, display a clear placeholder and allow the user to assign a replacement.

Do not claim that changing a material in the browser automatically edits the original GTA V material or shader metadata.

6. REAL EXPORTING

Implement working exports, not simulated download buttons.

Initially support:

* GLB export with supported geometry, materials, and embedded textures.
* GLTF export with the necessary associated files.
* OBJ export with appropriate material files and textures when supported.
* STL export for geometry-only use cases.

Use suitable exporters and ensure each export corresponds to the actual current scene, including supported transformations and material edits.

Requirements:

* Let the user choose the export format.
* Allow a filename.
* Generate a real downloadable file.
* Bundle multi-file exports in a ZIP when necessary.
* Preserve texture references correctly.
* Show export progress and errors.
* Never report success before the file has actually been generated.
* Re-import exported files when practical to verify that they can be loaded.
* Explain format limitations, such as STL not preserving ordinary materials and textures.

Keep the source project unchanged until the user saves or confirms changes.

7. PROJECT MANAGEMENT

Implement:

* New project.
* Open project.
* Save project.
* Save as.
* Rename project.
* Recent projects.
* Unsaved-changes warning.
* Undo and redo.
* Restore a saved project.

Create a project format that stores the scene structure, supported transforms, material settings, and required asset data.

Do not rely exclusively on temporary browser object URLs for saved projects.

Use IndexedDB for practical local persistence and project recovery. Architect the storage layer so cloud accounts and private cloud project storage can be added later.

Make it clear whether a project is saved locally or in cloud storage.

8. GTA V AND FIVEM FORMAT FOUNDATION

The target audience works with FiveM and GTA V assets, so design the application to support future integration with specialized GTA file-processing tools.

Common target formats include:

* YFT
* YTD
* YDR
* YDD
* YBN
* Related metadata and vehicle resource files.

For this first release, do not falsely claim that Three.js can directly import or export these formats.

Create a clean adapter interface for specialized GTA asset processors. Keep GTA-specific processing separate from the browser’s general-purpose 3D scene engine.

If a genuine processor is not integrated for a particular format:

* Clearly mark it as unsupported or not yet implemented.
* Explain what the format is used for.
* Preserve the original file.
* Do not generate a fake or renamed file with an incorrect extension.
* Do not claim that an ordinary GLB export is a valid GTA V vehicle.

Design future integration points for Blender, Sollumz, CodeWalker-compatible workflows, and appropriate GTA V asset libraries, subject to their actual capabilities and licensing.

Do not install random unverified binaries or execute uploaded files directly.

9. ARCHITECTURE AND SECURITY

Use a maintainable architecture with reusable components and strict TypeScript types.

Suggested modules:

* ViewportEngine
* SceneManager
* ImportManager
* ExportManager
* MaterialManager
* TextureManager
* ProjectManager
* FileValidation
* FormatAdapters
* OperationHistory

Security requirements:

* Validate file types and file sizes.
* Treat uploaded files as untrusted.
* Avoid executing uploaded scripts or model-provided executable content.
* Sanitize filenames.
* Handle malformed files safely.
* Never expose API keys in frontend code.
* Keep server secrets in environment variables.
* Avoid uploading private files to external services without user consent.

The viewport should work without requiring an AI API key.

Keep the architecture ready for a future AI assistant that can execute approved, reversible scene operations.

10. PERFORMANCE AND RELIABILITY

* Load large models without freezing the entire UI where practical.
* Display progress during loading and export.
* Handle WebGL errors and context loss.
* Clean up resources when projects change.
* Provide clear error messages and recovery options.
* Avoid losing unsaved changes.
* Ensure the layout remains responsive while loading.
* Test with models containing multiple meshes and materials.
* Verify that exported files can be opened by compatible software.

11. ACCEPTANCE TESTS

Do not consider the first release complete until these workflows work:

TEST A: Import a valid GLB, see the actual model, rotate it, zoom, select objects, and inspect the scene hierarchy.

TEST B: Import an OBJ and its MTL and texture files, confirm that the materials load correctly, and inspect the result.

TEST C: Replace a material texture with a PNG and confirm that the actual model updates immediately.

TEST D: Modify an object’s position, rotation, and scale, then export to GLB and verify that the changes persist when re-imported.

TEST E: Export a model to OBJ with its supported materials and associated texture files.

TEST F: Save a project, reload the application, and recover the saved scene.

TEST G: Repeat essential import, texture replacement, and export workflows on a mobile phone.

TEST H: Attempt to import an unsupported or invalid file and verify that the application reports the problem instead of crashing or claiming success.

12. BUILD STRATEGY

First inspect the environment and create a brief implementation plan. Then build the application in working milestones:

Milestone 1: Responsive interface, functional viewport, GLB/GLTF import, and scene controls.

Milestone 2: OBJ import, object hierarchy, selection, transforms, undo, and redo.

Milestone 3: Texture Studio, material editing, GLB export, and OBJ export.

Milestone 4: Project persistence, mobile testing, error handling, performance improvements, and format validation.

Build and test each milestone before continuing. Resolve actual runtime and TypeScript errors instead of hiding them.

Do not stop after producing the design. Run the application, test its primary workflows, and fix broken interactions.

Final objective: Deliver a premium, usable 3D asset workshop that genuinely imports supported models, edits real materials and textures, and exports real files. The first version must work independently of any future GTA V-specific converter or AI editing service.
